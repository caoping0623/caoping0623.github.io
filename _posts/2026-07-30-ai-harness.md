> 如果你做过车载开发，你一定见过 **test harness（测试架）**：把被测软件放进去，外面接仿真器、喂信号、采日志、判通过/失败。
>
> AI 圈子最近一年反复提的 **Harness**，本质上是同一类东西——**不是模型本身，而是把模型包起来、让它能干活、能自检、能被管住的那一整套工程环境。**
>
> 这篇文章写给工程师，尤其是车载方向的同事。看完你应该能回答三件事：Harness 到底指什么、工程里怎么落地、车载场景能不能用、怎么用才不踩安全红线。

## 一、用测试架理解 Harness

### 1.1 和 SIL 测试架对照

以 **SIL（Software-in-the-Loop，软件在环）** 为例：

| 角色 | SIL 里是什么 | AI 里对应什么 |
| --- | --- | --- |
| **被测对象** | 控制器算法 / ECU 软件 | 大模型（LLM） |
| **环境 / 台架** | 车辆动力学模型、传感器仿真、CAN 总线仿真 | 仓库、文档、工具、浏览器、诊断接口 |
| **测试架（Harness）** | 激励注入、I/O 映射、断言、日志、复位、故障注入 | **工具调用、权限、记忆、校验环、审批门、观测与回放** |
| **判定** | 通过/失败、覆盖率、时序是否满足 | 任务是否完成、测试是否绿、是否越权 |

**「环境 / 台架」这一行**两边列的都是**例子**：被测件外面那个「它以为自己连着的世界」。SIL 里是仿真车世界；Agent 里是工程世界（代码仓、文档、脚本、诊断通道等）。Harness 是夹具；环境是夹具接上去的那一侧。

SIL/HIL 里你绝不会说：「算法够强就行，台架随便搭。」  
AI 里同理：**模型再强，没有 harness，它也只是会说话的计算器**；有了 harness，它才变成能在真实工程环境里做事的 Agent。

联合国大学（UNU）2026 年的报告把这件事说得很清楚：

> Harness 是模型与环境之间的**运行时层**：负责把模型输出变成工具调用、观测、记忆更新、审批、中断、恢复和可回滚动作。

一句话公式：

```text
Agent ≈ 模型 + Harness
```

换模型，能力可能变；**换 harness，可靠性和安全性往往变得更明显。**

### 1.2 为什么现在突然人人都在说 Harness

过去几年大家经历了三轮重点迁移：

| 阶段 | 大致时间 | 大家在卷什么 | 要解决的典型问题 |
| --- | --- | --- | --- |
| Prompt Engineering | 2022–2024 | 怎么把话说清楚 | 同一句话换个说法结果就飘 |
| Context Engineering | 2024–2025 | 给模型喂什么上下文 | 材料太多/太少/不相关 |
| **Harness Engineering** | 2025–2026 | **怎么让模型在系统里稳定、可控地行动** | 会做但会闯祸、做一半丢状态、不会自检 |

HashiCorp 联合创始人 **Mitchell Hashimoto** 在 2026 年 2 月的文章《My AI Adoption Journey》里给了最直白的工程定义：

> 每当发现 Agent 犯了一次错，就花时间工程化一个解法，让它**以后再也不犯同样的错**。他把这叫 **harness engineering**。

注意：这里「工程化」不是再骂模型一句「下次注意」，而是改 **harness（夹具）**——加规则、加脚本、加测试、加权限门。

### 1.3 先把三个容易混的词拆开

| 概念 | 它干什么 | 主要谁在用 | 一句话 |
| --- | --- | --- | --- |
| **Agent Harness（运行时架）** | 让模型能行动：工具、记忆、循环、权限、恢复 | 用 Cursor / Copilot 等写代码、做业务开发的人 | **跑系统** |
| **Test Harness（经典测试架）** | 激励 + 观测 + 断言，验证软件行为 | 写单测、搭 SIL/HIL 的开发 / 测试工程师 | **验软件** |
| **Eval Harness（评测架）** | 用固定用例/指标重复打分，保证可比、可复现 | 要对比模型、做黄金集打分的人（平台 / 质量 / 部分开发） | **打分数** |

三者都叫 harness，因为结构相似：**把「被测/被驱对象」固定住，外面用夹具把输入输出和判定标准化。**  
本文重点讲 **Agent Harness**，评测架会单独一节带过，经典测试架用来当对照。

## 二、Agent Harness 里面到底有什么

把 harness 拆成六块积木。你可以把它想成「AI 版的台架机柜」：

### 2.1 上下文管道（Context Pipeline）

决定模型「上班前能看到什么」：

- 项目规则：`AGENTS.md` / Cursor Rules / Skill
- 相关代码与文档检索
- 接口定义、编码规范、安全红线

没有它，模型就像新入职同事没看过架构图，上来就乱改。

### 2.2 工具层（Tools）

模型不能直接拧螺丝，只能**提议调用工具**。工具可以是：

- 读/写文件、跑终端命令、查 Git
- 浏览器、数据库、工单系统
- 通过 [MCP]({{ '/2026/07/28/function-calling-mcp-skills/' | relative_url }}) 暴露的标准化工具

这和 ECU 不能「直接想象」车速、必须通过传感器接口拿信号，是同一逻辑。

### 2.3 校验环（Verification Loop）——最关键的一块

Hashimoto 强调的重点就在这里：**给 Agent 快速、高质量的「你错了」信号。**

常见校验器：

- 编译 / 类型检查
- 单元测试 / 静态分析
- 格式化与 lint
- 自定义脚本（比如「禁止改安全相关文件」「差分必须带测试」）

没有校验环，Agent 容易「自我感觉良好地交付烂结果」。  
有了校验环，它像进了带仪表的台架：动作一出，立刻有红灯绿灯。

### 2.4 权限与审批（Guardrails）

决定哪些动作可以自动做，哪些必须人点头：

| 动作类型 | 典型策略 |
| --- | --- |
| 只读：搜代码、读日志 | 可自动 |
| 本地可逆改动：改业务代码 + 跑测 | 可自动或轻确认 |
| 高风险：`git push --force`、删库、改安全标定、写实车 | **必须人工审批 / 直接禁止** |

车载语境下，这一层几乎是硬需求。

### 2.5 记忆与状态（Memory / State）

长任务需要记住：做到哪一步了、上次失败原因、用户偏好、项目约定。  
联合国大学（UNU）报告里提到的常见失败，很多都是状态问题：中断后重复操作、上下文溢出后「失忆」、无法恢复。

### 2.6 观测与回放（Observability）

记录：调了什么工具、入参出参、花了多久、失败在哪一层。  
没有 trace，你只能抱怨「AI 不行」；有了 trace，你才能改 harness。

## 三、工程里怎么实际应用（详细例子）

下面几个例子故意写细，方便你对照自己团队现状。

### 3.1 例子一：编码 Agent 的「防重复踩坑」架（最通用）

**场景**：用 Cursor / Claude Code 改一个模块，它反复犯同一类错。

**坏做法**：每次聊天里骂它「别再这么写」。明天新会话，它照犯。

**Harness 做法**（Hashimoto 路线）：

1. **观察到错误**：Agent 总爱在车载工程里用宿主机路径写死配置，CI 挂掉。
2. **工程化一次**：
   - 在 `AGENTS.md` 加一条：「禁止硬编码绝对路径；配置必须走相对路径 + 环境变量。」
   - 加一个脚本 `scripts/check_no_abs_path.py`，扫描 diff。
   - 在规则里写：「改完必须跑 `python scripts/check_no_abs_path.py`」。
3. **下次**：Agent 若再犯，校验环立刻红灯，它自己改，而不是等你发现。

这就是 harness engineering 的「棘轮」：**错误变成永久夹具，而不是永久嘴炮。**

### 3.2 例子二：让检查结果「当场」告诉 Agent，别等集成人员来找你

先澄清两个容易误会的点：

**CI 不只是集成人员的事。**  
CI（持续集成）是仓库上那套自动检查：一推代码或提 PR，就自动编译、跑单测、做静态检查。流水线往往由平台/集成同事维护，但**每次检查验的是你刚改的代码**。开发人员一样会撞上 CI 红灯；用 AI 写代码时，更应该在说「做完了」之前，先跑通和 CI 同类的检查。

**改造前（很常见）**：

1. 你让 AI 改一段代码  
2. AI 说「改好了」  
3. 你提交 / 提 PR，过很久 CI 才红  
4. 集成或你自己再回来找 AI 重改——又慢又费事

**改造后（harness 思路）**：

1. AI 改代码  
2. **立刻**在本地跑和 CI 类似的检查（至少：能编过、相关单测过、lint/自定义脚本过）  
3. 红了 → 把报错原文喂给 AI，让它继续改，再跑一遍  
4. 绿了 → 才允许说完成，再提 PR 给人 Review  

伪流程：

```text
循环直到通过（或明确需要人接手）：
    AI 改一版
    跑：编译 + 单测 + lint（能本地跑的先本地跑）
    若失败：
        把失败日志回给 AI
    若成功：
        整理变更说明，等人 Review
```

对车载开发，个人电脑上至少先接上这些校验：

- 你改的那个模块能编译  
- 相关 GoogleTest / 现有单测  
- 已有的静态检查（仓库里若已有 MISRA 等脚本，就接上；没有也不必硬造一整套 CI）

远端 CI 仍然有用：它是合码前的第二道闸。但**第一道闸应在开发侧**，否则 AI 每次都要等集成流水线红了才知道错——反馈太慢，改起来也费劲。

### 3.3 例子三：Eval Harness——别用「感觉」换模型

**场景**：领导问：「换个更强的模型，诊断助手会不会更好？」

没有评测架，你只能靠几个人主观试。有了 **Eval Harness**，你可以：

1. 固定一批用例（比如 50 条真实脱敏诊断问答）
2. 固定评分方式（关键字段是否抽对、是否胡编 DTC、是否给出危险建议）
3. 同一 harness 配置下跑模型 A / B
4. 得到可复现分数

开源里最出名的是 EleutherAI 的 **lm-evaluation-harness**（偏学术基准）；工程团队更常见的是自建「黄金集 + 自动判分」。

记住对比：

| | Agent Harness | Eval Harness |
| --- | --- | --- |
| 目的 | 让系统能干活 | 让对比可复现 |
| 输入 | 真实任务环境 | 固定用例集 |
| 输出 | 产物/动作 | 分数/报告 |

两者常一起用：**用 agent harness 跑任务，用 eval harness 量好坏。**

### 3.4 例子四：权限分层——「能读日志，不能直接刷写」

**要解决的问题：**  
诊断辅助 Agent 很能干，但有的动作只是「看看、说说」，有的动作会真的改车、改 ECU。不能让模型一提议就自动执行所有事。

**权限分层长什么样（举例）：**

| Agent 想做的事 | 怎么处理 | 为什么 |
| --- | --- | --- |
| 解析 `.asc` / `.blf` 总线日志 | ✅ 可以自动做 | 只读，弄坏不了车 |
| 查内部 DTC 知识库 | ✅ 可以自动做 | 只读 |
| 列出可能原因、给排查建议 | ✅ 可以自动做 | 只是文字，人再判断 |
| 生成刷写脚本 / 命令草稿 | ⚠️ 可以写到文件里给人看 | **默认不许执行**；执行要人点头 |
| 通过诊断仪真下发、刷写 | ❌ 禁止，或必须人审批且确认在台架 | 一做错就可能变砖、有安全风险 |

**这些权限写在哪里？**  
不是写在模型脑子里，而是写在 **harness 配置**里，例如：

- 规则 / `AGENTS.md` / Skill：写明「哪些目录可写、哪些命令禁止、刷写相关只能出草稿」
- 工具开关：根本不给 Agent 注册「下发刷写」这类工具；或注册了但默认拒绝调用
- IDE / 产品权限：Cursor 等对终端命令、敏感路径的确认或拦截
- 环境标识：只有检测到「当前是台架/仿真」才允许更高权限；连着实车时一律禁止

模型可以**建议**「该刷写了」，但真正按按钮的必须是人（或另一道硬闸门）。

**一句话记住：**  
危险的事先默认拦住；只有人确认、并且环境对（例如台架而不是实车）才放开。这和功能安全里「不确定就先安全侧」是同一类想法，并不是跟 AI 过不去。

### 3.5 例子五：和本站已有概念怎么拼

如果你读过 [Function Calling / MCP / Skills]({{ '/2026/07/28/function-calling-mcp-skills/' | relative_url }})：

| 零件 | 在 Harness 里扮演什么 |
| --- | --- |
| Function Calling | 模型「会不会填工具表单」 |
| MCP | 工具怎么标准化接入 |
| Skills / AGENTS.md | 操作手册与领域约束 |
| 权限 / 沙箱 / CI | 安全与校验环 |
| Trace / 日志 | 观测与改进依据 |

**Harness 是总装；MCP/Skills 是总装里的线束和 SOP（Standard Operating Procedure，标准作业程序 / 操作规范）。**

## 四、车载领域能不能用？能，而且很对口

本章按**车载软件 / 诊断开发人员**来写（改代码、查日志、出配置与设计说明），不展开测试同事专属的用例库、SIL 回归场景建设。

结论先说：

> **能用。** 开发日常里的规则、编译校验、路径权限、日志工具，本来就很像一套夹具；把同样纪律套到 AI 上即可。  
> 但有一条硬边界：**量产安全相关路径上，Agent 只能辅助，不能绕过既有安全与质量体系自动闭环。**

### 4.1 你身边其实已有「夹具思维」

就算你不搭 SIL/HIL，下面这些开发侧习惯，和 AI Harness 是同一类结构：

| 开发里已有的做法 | 和 AI Harness 的对应 |
| --- | --- |
| 本地编译 / 模块构建脚本 | 校验环（改完先过编译） |
| Code Review、目录权限、不能乱改诊断表 | 权限与审批 |
| DBC、接口文档、架构说明、历史 Issue | 上下文管道 |
| 总线日志、诊断仪、内部 Wiki | 工具 / 环境 |
| 提交规范、CI 红灯 | 观测与反馈 |

所以学 AI harness，不是另起炉灶，而是：**把你已经用来管代码的那套纪律，明确写给 Agent。**

### 4.2 车载开发里现在就能落地的 6 个场景（从易到难）

#### 场景 A：知识问答（架构、接口、历史问题）（最容易先做）

**痛点**：新人或不熟模块的同事，反复问「这个 DID 谁实现的」「上次类似问题怎么修的」。

**Harness 设计**：

1. 只读接入 Wiki / 代码仓 / 设计文档检索  
2. 答案必须带出处链接  
3. 无出处时必须说「未找到」，禁止把猜测写成规范结论  

**价值**：onboarding 和日常答疑快；几乎不碰量产代码。

#### 场景 B：CAN / 以太网日志辅助分析

**痛点**：实车或台架复现后，要在海量帧里找「谁先异常」。

**Harness 设计**：

1. 工具：解析日志、按信号过滤、对齐时间轴、导出片段  
2. 知识：DTC 含义、DBC 信号字典只读接入  
3. 强制输出模板：时间线 → 可疑信号 → 假设 → **需要你确认的点**  
4. 禁止：根据日志直接宣称「根因已确认」或自动提维修/刷写工单  

**价值**：加快定位；结论仍由开发人员拍板。

#### 场景 C：诊断 / 配置产物辅助生成（很贴日常开发）

**痛点**：从需求 Excel、接口表生成 TOML / ARXML / Handler 草稿，手工又慢又容易漏字段。

**Harness 设计**：

1. **输入**：需求表、既有配置样例、项目 `.oda-harness/`（或同类）配置  
2. **工具**：只允许写到约定的生成/草稿目录；跑项目里的生成器与校验脚本  
3. **校验**：必填字段是否齐、命名是否符合规范、生成命令是否退出码 0  
4. **人工**：你 Diff Review 后才合入业务仓  

**价值**：把重复劳动交给 Agent，用脚本红灯兜住格式错误——这正是 ODA-Harness 一类 toolkit 在干的事。

#### 场景 D：工具链 / 脚本卫生（最适合练手）

车载仓库常有：Python 转换脚本、DBC 处理、日志切割、版本打包。

这些**非行车安全路径**是 Agent + Harness 的最佳练兵场：

- 改脚本 → 跑脚本自带检查 / 用样例数据回归 → 出 PR  
- 失败就把日志回灌，直到绿  

先在这里把「改完必须校验」跑顺，再让 Agent 靠近控制器代码。

#### 场景 E：模块代码助手（应用层），带车规约束

**痛点**：AI 写的代码「能编过」但不合规：热路径动态内存、忽略返回值、乱改诊断映射。

**Harness 设计（很车载）**：

在规则里写死，例如：

```text
本仓库为车载嵌入式 C 工程：
1. 禁止在热路径使用动态内存分配
2. 所有外部调用必须检查返回值
3. 修改安全相关目录（Safety/）前必须停下等待人工确认
4. 每次改动后必须运行模块编译脚本（如 west build / 仓库规定的 build）
5. 提交信息必须关联 Issue ID
```

再配上：

- 模块编译作为硬校验（有模块级单测也可接上，没有也不必硬造测试体系）  
- `Safety/`、`diag/` 等目录默认只读或需审批  
- diff 扫描禁用 API 列表  

这时 Agent 不是「更聪明」，而是「被夹具夹住后更可靠」。

#### 场景 F：接口 / 需求变更 → 影响分析与改码清单

**痛点**：变更一来，要翻接口文档、找调用点、估影响面，容易漏。

**Harness 设计**：

1. **输入**：变更说明、需求/接口 ID、相关头文件与调用检索  
2. **输出模板**：影响模块列表 → 建议改动点 → 风险与待确认项（必须标「需人工确认」）  
3. **写入范围**：默认只写分析文档或草稿补丁；合入前必须人 Review  
4. **禁止**：在未确认影响面时直接大面积改多仓代码  

**价值**：帮你把「该看哪里」列全；真正改哪里仍由你决定。

### 4.3 一张「能不能上 Agent」的车载开发决策表

| 工作内容 | 建议 | 原因 |
| --- | --- | --- |
| 文档检索、日志解读、脚本工具、配置草稿 | ✅ 积极用 | 可逆、可审、收益高 |
| 应用层非安全模块 + 本地编译等硬校验 | ✅ 可用 | harness 能兜住大部分错 |
| 安全相关软件（ASIL 路径）、标定、刷写、实车控制 | ⚠️ 仅辅助，禁止自动闭环 | 责任与标准不允许黑盒自治 |
| 生成 ISO 26262 / ASPICE 证据并自动签字 | ❌ 不行 | 证据链与责任必须由组织流程承载 |

### 4.4 一个完整的车载小案例：从「翻车」到「夹具」

**背景**：团队让 Agent 改 BCM 里一个门控相关的应用模块。

**第一次翻车**：

1. Agent 改完宣称成功  
2. 本地没跑目标板编译  
3. CI 在 QNX 交叉编译挂了  
4. 还误改了旁边的诊断映射表  

**按 harness engineering 改造**（一次性投入，长期收益）：

| 翻车点 | 加到 harness 的东西 |
| --- | --- |
| 没编译就说完成 | 规则：完成前必须跑 `./scripts/build_bcm.sh`；失败不得结束 |
| 乱改诊断表 | 路径守卫：`diag/` 默认只读；要改必须明确审批 |
| 提交说明混乱 | 钩子：commit message 必须含 `JIRA-xxxx` |

**第二次**：

Agent 改代码 → 编译红 → 自修 → 绿 → 生成 PR 说明（含风险点）→ **你做 Review**。

模型可能还是同一个。变强的是 harness。

## 五、怎么动手搭一个最小可用 Harness

哪怕只有你一个人，也可以从最小闭环开始：

### 5.1 最小四件套

1. **规则文件**：`AGENTS.md` 或 Cursor Rules（写清仓库禁忌与完成定义）  
2. **一个校验脚本**：例如 `make verify` = 编译 + 单测 + 自定义检查  
3. **权限边界**：哪些目录可写、哪些命令禁止  
4. **一次失败归档**：每次 Agent 翻车，沉淀 1 条规则或 1 个检查

### 5.2 「完成定义」要写成机器可执行的

坏的完成定义：

> 把功能做好。

好的完成定义：

```text
完成必须同时满足：
1) ./scripts/build.sh 退出码 0
2) ctest -R door_ 全部通过
3) scripts/check_no_todo_in_diff.py 通过
4) 输出变更说明，列出风险与未覆盖测试
否则不得声称完成。
```

Agent 是目标导向的：你给的目标含糊，它会走捷径；你给的目标可机检，它才被「夹」回正轨。

### 5.3 和 Cursor / Hermes / WorkBuddy 的关系

| 产品 | 你看到的 | 底下的 harness 味道 |
| --- | --- | --- |
| Cursor | 改代码的 Agent | 工具 + 规则 +（可配）权限与终端策略 |
| Hermes | 个人 Agent 框架 | Skills、MCP、定时、多端投递 |
| WorkBuddy | 办公桌面 Agent | 工作空间、连接器、Skill、结果验收 |

选产品是选「现成 harness」；**真正拉开差距的，是你有没有把领域约束和校验环写进去。**

## 六、常见误区

| 误区 | 纠正 |
| --- | --- |
| 「换更强模型就行」 | 很多故障在 harness：没工具、没校验、没权限、没记忆 |
| 「多写点 prompt 就等于 harness」 | Prompt 只是一层；缺脚本/测试/权限门时，prompt 挡不住重复犯错 |
| 「有 harness 就可以无人值守上实车」 | 车载安全路径必须保留人与流程；harness 是辅助加速，不是替代认证 |
| 「评测就是跑几个 demo」 | 没有固定用例与评分，换模型对比没有工程意义 |
| 「一次配完美」 | harness 是演化的：每次失败加一根「钢筋」 |

## 七、总结

### 7.1 记这三句就够

1. **Harness = 模型周围的工程夹具**：工具、上下文、校验、权限、记忆、观测。  
2. **Harness Engineering = 把每次翻车变成永久防护**，而不是永久抱怨。  
3. **车载开发不但能用，而且很划算**——编译、目录权限、提交规范本来就是夹具；写给 Agent 之后，重复劳动和低级失误会少很多。

### 7.2 对车载同事的行动建议

- **本周**：挑脚本、文档或诊断配置草稿路径，写下 `AGENTS.md` + 一条本地编译/校验命令  
- **本月**：给 `Safety/`、`diag/` 等危险目录加门  
- **本季**：再评估是否让 Agent 辅助应用层改码；安全相关仍保持人审 + 既有流程

### 7.3 最后

模型像「潜在很强的新同事」。  
Harness 像「岗位说明书 + 权限卡 + 工装夹具 + 下线检测」。

车载行业从来不缺对夹具的尊重——缺的只是把这套尊重，明确地用到 AI 上。

> 与其问「这个模型聪不聪明」，不如问「我们有没有给它一台合格的台架」。
